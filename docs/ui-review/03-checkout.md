# 03 — صفحة إتمام الطلب `/checkout`

**الملف:** `client/src/pages/Checkout.tsx` (28,630 بايت)
**المسار:** `/checkout`
**الشخصية:** الاتنين (firm + company) — بتُقرأ من `?persona=`
**نوع المراجعة:** قراءة كود (مش رندر فعلي — الشبكة مقفولة في بيئة المراجعة)

---

## 0. ليه الصفحة دي أهم صفحة في المشروع كله

الزائر اللي وصل هنا **دفع تمن نفسي بالفعل**: اختار شخصية، قرأ الأسعار، وضغط زر. كل جنيه اتصرف على جذبه بقى محبوس في الصفحة دي. أي تشويش هنا مش بيقلل التحويل — بيلغيه.

ولذلك ترتيب الأولويات في الملف ده مختلف: **P0 هنا = فقدان فلوس مباشر**، مش «تحسين تجربة».

---

## 1. ترتيب الأقسام الحالي

| # | القسم | الحالة |
|---|---|---|
| — | شريط علوي: لوجو + «الرجوع إلى الصفحة الرئيسية» | ✅ |
| — | Stepper بـ3 خطوات | ⚠️ ثابت + مقلوب |
| 1 | بيانات النشاط والتواصل (اسم / موبايل / إيميل) | ⚠️ في المكان الغلط |
| 2 | تأكيد باقة الاشتراك (`RadioGroup`) | ⚠️ باقات الشخصية الغلط |
| 3 | نوع الاشتراك وفترة الصلاحية | ℹ️ عرض فقط |
| 4 | الإضافات وسعات التشغيل (3 كروت + stepper كمية) | 🔴 فرصة بيعية مهدرة |
| 5 | وسيلة الدفع المفضلة (3 كروت) | 🔴 اختيار وهمي |
| — | زر «متابعة لتأكيد الدفع التجريبي» | ⚠️ |
| — | `aside` ملخص أمر الشراء (داكن، sticky على الديسكتوب فقط) | 🔴 مش موجود فعليًا على الموبايل |

**فيه نظامين ترقيم متعارضين على نفس الشاشة:** الـStepper بيقول 3 خطوات، والفورم بيقول 5 أقسام مرقّمة 1–5. الزائر مش عارف هو في خطوة كام من كام.

## 2. العيوب المرقّمة

### 🔴 P0-1 — الشركة اللي اختارت 850 بتوصل الشيك أوت وهي على باقة مكتب بـ500

**الملاحظة:** الشخصية بتتفقد من باراميتر اسمه `persona`، لكن الصفحة الرئيسية بتكتب الشخصية في باراميتر اسمه `p`. الاسمين مختلفين، فالقراءة بتفشل دايمًا.

**الدليل من الكود:**
```ts
// Checkout.tsx
const persona: "firm" | "company" = search.get("persona") === "company" ? "company" : "firm";
const availablePlans = useMemo(() => getPlansForPersona(persona), [persona]);
const initialPlan = search.get("plan") ?? sessionStorage.getItem("mof_selected_plan") ?? availablePlans[0].sku;
const [planSku, setPlanSku] = useState(
  availablePlans.some((item) => item.sku === initialPlan) ? initialPlan : availablePlans[0].sku
);
```
في `Home.tsx` الشخصية بتتكتب على `?p=`. يعني `search.get("persona")` بترجع `null` ⇒ الشخصية بتتحوّل لـ`firm` افتراضيًا.

**سلسلة الفشل بالكامل:**
1. شركة تختار «الباقة الخاصة» (`special`, 850) على الصفحة الرئيسية.
2. `sessionStorage.mof_selected_plan = "special"`.
3. تروح `/checkout` ⇒ `persona` بترجع `firm`.
4. `availablePlans` = باقات المكاتب: `professional / expert / consultant / elite`.
5. `availablePlans.some(sku === "special")` ⇒ **false**.
6. `planSku` بيقع على `availablePlans[0].sku` = **`professional`** بـ**500 ج.م**.
7. الـ`aside` بيقول «باقة مكتب محاسبة» و«باقة المحترف»، والإضافات بتتغيّر، والإجمالي بيتغيّر.

**الأثر البيعي:** الشركة بتشوف حاجة **مش اللي اختارتها خالص** — لا نفس الاسم، لا نفس السعر، لا نفس الشخصية. ده مش عيب تجربة، ده **إلغاء الطلب**. والأسوأ: لو كمّلت، الأوردر بيتسجل `persona: "firm"` وباقة غلط في قاعدة البيانات.

**والاتجاه العكسي كذلك:** مكتب اختار `elite` (2500) → لو الشخصية اتقروت `company` بأي شكل، بيقع على `founder` بـ250. **فرق 2,250 ج.م في الأوردر الواحد.**

**الإصلاح:**
1. وحّد اسم الباراميتر. اختار `?persona=` واحد بس واستخدمه في الكتابة والقراءة، وسيب `?p=` كـalias مؤقت للتوافق:
   ```ts
   const rawPersona = search.get("persona") ?? search.get("p");
   const persona = rawPersona === "company" ? "company" : "firm";
   ```
2. **الأهم:** اشتق الشخصية من الباقة، مش العكس. الباقة نفسها فيها الشخصية في `shared/poc.ts` (فيلد `persona`):
   ```ts
   const requestedSku = search.get("plan") ?? sessionStorage.getItem("mof_selected_plan");
   const requestedPlan = PLANS.find((p) => p.sku === requestedSku);
   const persona = requestedPlan?.persona ?? rawPersona ?? "firm";
   ```
   كده الباقة هي مصدر الحقيقة ومستحيل يحصل عدم تطابق.
3. اقرأ كمان `sessionStorage.mof_persona` كطبقة احتياطية تالتة.
4. **لو حصل عدم تطابق فعلًا، متبدّلش في السكوت.** اعرض شريط: «كنت مختار الباقة الخاصة — رجّعها؟» بزر واحد. الاستبدال الصامت هو الجزء المدمّر، مش الخطأ نفسه.

### 🔴 P0-2 — الزائر بيختار وسيلة دفع، والاختيار بيتم رميه

**الملاحظة:** قسم «5. وسيلة الدفع المفضلة» بيخزّن الاختيار في state محلي مش مستخدم في أي حاجة تانية.

**الدليل من الكود:**
```ts
const [selectedPaymentMethod, setSelectedPaymentMethod] = useState<string>("card");
```
ودورة حياة الـstate دي بتنتهي عند التلوين. مفيش أي استخدام تاني — مش موجود في:
```ts
createOrder.mutate({
  visitorId: context.visitorId, persona,
  name: ..., email: ..., phone: ...,
  planSku, addonQuantities, billingCycle: cycle,
});
```
وفي `DemoPayment.tsx` الصفحة بتبدأ من الأول:
```ts
const [activeTab, setActiveTab] = useState<"card" | "fawry" | "wallet">("card");
```

**الأثر البيعي:** الزائر يختار «فوري» بوعي وقصد، يضغط متابعة، وتفتحه الصفحة الجديدة على **«بطاقة بنكية»**. الرسالة اللي بتوصل: «الموقع ده مش بيسمعني». في لحظة الدفع بالتحديد، دي أغلى رسالة ممكن تبعتها. وبعدها بيختار تاني — **نفس القرار مرتين** = تشويش صريح وضد هدفك المعلن (تسهيل القرار وعدم التشتيت).

**الإصلاح — تلاتة اختيارات، مرتّبين بالأفضلية:**
1. **الأفضل:** شيل القسم 5 من الشيك أوت بالكامل. وسيلة الدفع قرار بيتاخد على البوابة، مش قبلها. كده تقلل خطوة وتمنع التعارض من الأصل.
2. لو عايز تسيبه: مرّره فعليًا — `paymentMethod` في `createOrder`، وفي جسم الأوردر، ويُقرأ في `DemoPayment` كتاب افتراضي:
   ```ts
   const [activeTab, setActiveTab] = useState(session.data?.paymentMethod ?? "card");
   ```
   (مع مراعاة إن `session.data` بتوصل بعد التحميل ⇒ استخدم `useEffect` أو `key`).
3. الحل الأسرع مؤقتًا: مرّره في الـURL — `/demo-payment/${token}?pm=${selectedPaymentMethod}`.

### 🔴 P0-3 — على الموبايل، الزائر بيملّي الفورم كله وهو مش شايف السعر

**الملاحظة:** ملخص أمر الشراء sticky على الديسكتوب بس، وفي ترتيب الـDOM جاي **بعد** الفورم.

**الدليل من الكود:**
```tsx
<div className="grid gap-8 lg:grid-cols-[1.1fr_0.9fr] items-start">
  <form ...>  {/* 5 أقسام */}  </form>
  <aside className="... lg:sticky lg:top-8">  {/* الملخص والإجمالي */}  </aside>
</div>
```
تحت `lg` الشبكة بتبقى عمود واحد ⇒ الـ`aside` ينزل تحت خمس أقسام كاملة. و`lg:sticky` معناها إنه **مش** sticky على الموبايل. ومفيش أي شريط سفلي ثابت في الصفحة.

**الأثر البيعي:** أغلب الترافيك المصري موبايل. الزائر بيدخل بياناته الشخصية، يختار باقة، يزوّد إضافات — **وهو معندوش أي فكرة عن الإجمالي** لحد ما يوصل آخر الصفحة. وكل مرة يضغط `+` على إضافة، الرقم اللي بيتغيّر **بره الشاشة**. الـfeedback loop مكسور تمامًا: بيتصرف بدون نتيجة مرئية.

وده كمان مخالف صريح لـ`sales-funnel.md` §17 اللي بينص على شريط سفلي ثابت على الموبايل.

**الإصلاح:**
1. **شريط سفلي ثابت على الموبايل (`lg:hidden`)** فيه: الإجمالي على اليمين + زر «متابعة» على الشمال + سطر صغير «شامل الضريبة».
   ```tsx
   <div className="fixed bottom-0 inset-x-0 z-40 lg:hidden border-t border-[#4046B5]/15 bg-white/95 backdrop-blur px-4 py-3">
   ```
   مع `pb-24` على الحاوية الأساسية عشان مايغطّيش آخر عنصر.
2. **الرقم يتحرك لما يتغيّر.** أي تغيير في الإجمالي = أنيميشن `count-up` قصير (250ms) + وميض خفيف على خلفية الرقم. ده بيربط الفعل بالنتيجة فورًا ويخلّي الزائر يجرّب — والتجريب بيزوّد قيمة السلة.
3. على الموبايل خلّي الملخص كـ`<details>` قابل للفتح **فوق** الفورم كمان، مقفول افتراضيًا وعنوانه هو الإجمالي.

### 🔴 P0-4 — أكبر فرصة رفع متوسط الطلب في المشروع كله، ومفيش أي كود بيستغلها

**الملاحظة:** لو شركة اختارت `founder` (250) وضافت «حزمة الإصدار» (600) من القسم 4، الإجمالي بيبقى **850 بالظبط** — نفس سعر «الباقة الخاصة» اللي فيها كمان مستخدم تاني (50) وجهاز POS (500). الصفحة مش بتقول أي حاجة.

**الدليل من الكود:** الأرقام من `shared/poc.ts`:
- `founder` = `annualPiastres: 25000` (250 ج.م) — **من غير نقاط إصدار**
- addon `points` «حزمة الإصدار: 9600 نقطة» = `60000` (600 ج.م)، و`includedIn: ["special"]`
- `special` = `85000` (850 ج.م) + 9600 نقطة + 1 POS + 2 مستخدمين

والكود **عارف** العلاقة دي أصلًا:
```ts
useEffect(() => {
  Object.keys(next).forEach((sku) => {
    if (ADDONS.find((item) => item.sku === sku)?.includedIn?.includes(planSku)) {
      delete next[sku];
    }
  });
}, [planSku]);
```
يعني `includedIn` مستخدمة **لتنضيف السلة** لكن **مش** مستخدمة للترقية. المنطق مبني نصه وواقف.

**الأثر البيعي:** شركة هتدفع 850 وتاخد أقل حاجة، وإنت بتخليها تعمل كده بصمت. لما تكتشف بعدين، الإحساس بيبقى «الموقع خدعني» — وده أغلى من الفرق نفسه. والعكس: نفس اللحظة دي هي **أقوى نقطة إقناع في القمع كله**، لأن الزائر بالفعل قرر يدفع 850.

**الإصلاح — بلوك ترقية لحظي جوه القسم 4:**

الشرط: `planSku === "founder"` و`addonQuantities.points >= 1`.

```
┌─────────────────────────────────────────────┐
│  🟢  استنى ثانية — عندك نفس الفلوس أحسن     │
│                                             │
│  انت دلوقتي على:  250 + 600  =  850 ج.م     │
│  الباقة الخاصة:              850 ج.م        │
│                                             │
│  وفيها كمان:                                │
│    ✓ مستخدم تاني        (بـ50 ج.م)          │
│    ✓ جهاز نقطة بيع POS  (بـ500 ج.م)         │
│                                             │
│  يعني 550 ج.م زيادة — بنفس الرقم.           │
│                                             │
│  [ بدّلها للباقة الخاصة ]   لأ، كمّل كده     │
└─────────────────────────────────────────────┘
```

**قواعد التنفيذ:**
- الزر الواحد بيعمل `setPlanSku("special")` — والـ`useEffect` الموجود أصلًا هيشيل الـ`points` من السلة لوحده لأنها `includedIn`. **صفر كود جديد في منطق الحساب.**
- الأنيميشن هو الحجة نفسها: السطرين (250 / 600) يظهروا، بعدها علامة `=` ترسم، بعدها الـ850 تنزل بحركة الختم، بعدها البونصين يظهروا واحد ورا التاني بتأخير 80ms. **الحركة بترسم الاستنتاج مش بتزيّن.**
- خلي «لأ، كمّل كده» نص عادي مش زرار — الاختيار متاح بس مش متساوي بصريًا.
- استخدم الأخضر `#10B981` هنا وهنا بس في القسم — هو دلالة «القرار الأصح».
- اشتق كل الأرقام من `PLANS` و`ADDONS` وقت الرندر. **متكتبهاش يدوي** (نفس غلطة `sales.upsell.body` في تقرير LP-B).
- اتبع نفس المنطق للمكاتب: `professional → expert` وهكذا، لو الإضافات وصّلت لسعر الباقة الأعلى.

**تتبّع:** حدثين جديدين — `upsell_shown` و`upsell_accepted` مع `{from, to, deltaPiastres}`. ده أهم رقمين في الداشبورد بعد `checkout_started`.

### 🟠 P1-1 — الـStepper بيكدب: ثابت، ومقلوب، وبيتعارض مع ترقيم الفورم

**الملاحظة:** ثلاث مشاكل في عنصر واحد.

**الدليل من الكود:** الـStepper بيقول بالترتيب:
1. تأكيد الباقة والتفاصيل
2. بيانات الاتصال والنشاط
3. اعتماد الدفع التجريبي

والفورم تحته بالترتيب:
1. بيانات النشاط والتواصل
2. تأكيد باقة الاشتراك
3. نوع الاشتراك
4. الإضافات
5. وسيلة الدفع

**التشخيص:**
- **مقلوب:** خطوة 1 في الـStepper = قسم 2 في الفورم، والعكس.
- **ثابت:** الخطوة 1 دايمًا ملوّنة بالبنفسجي والباقي رمادي، من غير أي `state`. الزائر يوصل آخر الصفحة ولسه «خطوة 1». مفيش إحساس تقدّم خالص.
- **متعارض:** 3 أرقام فوق و5 أرقام تحت على نفس الشاشة.

**الأثر البيعي:** الـStepper المفروض وظيفته تقليل القلق («فاضل قد إيه؟»). في الشكل الحالي بيزوّد القلق ويضيف حمل إدراكي. وبما إن ده صفحة واحدة، الزائر بيحس إنه واقف مكانه.

**الإصلاح:** اختار **واحد** من التنين وامسح التاني:
- **(أ) الأنضف:** شيل الـStepper، وسيب ترقيم الأقسام 1–5 بس، وضيف بدلها **شريط تقدّم رقيق** مربوط بالأقسام المكتملة فعلًا (اسم + موبايل + إيميل + باقة). حرّكه بـ`transition-[width] duration-300`.
- **(ب)** خلّي الـStepper يمثّل الرحلة الحقيقية بين الصفحات: `الطلب → الدفع → العقد`، وشيل الترقيم من أقسام الفورم وسيبها عناوين. ده بيوصّل «فاضل خطوتين بس» وهي رسالة مطمّنة وصحيحة.

في الحالتين: الخطوة الحالية لازم تتحرك.

### 🟠 P1-2 — الأرقام معروضة بخط ملوش أرقام عربية

**الملاحظة:** كل سعر في الصفحة متغلّف بـ`font-[Inter]` وجوّاه ناتج `formatEgp`.

**الدليل من الكود:**
```tsx
<strong className="font-[Inter] text-2xl font-black text-white" dir="ltr">
  {quote.data ? formatEgp(quote.data.totalPiastres) : "…"}
</strong>
```
و`formatEgp` في `shared/poc.ts`:
```ts
new Intl.NumberFormat("ar-EG", { style: "currency", currency: "EGP", maximumFractionDigits: 2 })
```
`ar-EG` بيطلع أرقام عربية-هندية (٨٥٠) وعلامة عملة `ج.م.‏`. و**Inter ملوش جليفات للأرقام العربية-الهندية** ⇒ المتصفح بيهرب لخط بديل، فيحصل تغيّر في الوزن والعرض، وأحيانًا مربعات فاضية.

**وده بيحصل على أخطر رقم في المنتج كله:** الإجمالي النهائي.

**الأثر البيعي:** رقم السعر لازم يبان صلب وواضح ومقروء من مسافة. لو بان مهزوز أو بخط مختلف عن باقي الصفحة، الثقة بتنزل في اللحظة الحرجة بالظبط. وكمان `maximumFractionDigits: 2` معناها كسور على مبالغ الضريبة (زي `119.00`) — تشويش بصري بدون فايدة.

**الإصلاح:** في `shared/poc.ts`:
```ts
const egpFormatter = new Intl.NumberFormat("ar-EG-u-nu-latn", {
  maximumFractionDigits: 0,
});
export const formatEgp = (piastres: number) =>
  `${egpFormatter.format(piastres / 100)} ج.م`;
```
- `-u-nu-latn` = أرقام لاتينية (850) — متوافقة مع Inter.
- `maximumFractionDigits: 0` = بدون كسور.
- «ج.م» نص عربي عادي بيتعرض بـCairo — فشيل `font-[Inter]` من الحاوية وحُطّه على الرقم بس، أو استخدم `font-variant-numeric: tabular-nums` عشان الأرقام تتبدّل من غير ما العرض يقفز.
- شيل `dir="ltr"` من الحاوية الكاملة وحطّه على الرقم لوحده، وإلا «ج.م» بتقع على الشمال.

### 🟠 P1-3 — بتطلب بياناته الشخصية قبل ما يتأكد إنه بيشتري إيه

**الملاحظة:** قسم 1 = اسم + موبايل + إيميل. تأكيد الباقة قسم 2.

**الأثر البيعي:** أول حاجة الصفحة بتطلبها هي **عطاء** (بياناته)، قبل أي **تأكيد** (إنه فاهم بياخد إيه بكام). دي عكس الترتيب النفسي الصح: أكّد القيمة، بعدين اطلب. وعلى الموبايل بالتحديد، أول شاشة كلها حقول فاضية — أعلى معدل ارتداد ممكن.

كمان: لو حصل خطأ الشخصية (P0-1)، الزائر يكتشفه **بعد** ما يكون كتب تلات حقول. الغضب أكبر بكتير.

**الإصلاح:** اقلب الترتيب:
1. **الباقة المختارة** — كارت مقفول (مش راديو) فيه الاسم والسعر وزر نصي «تغيير».
2. **الإضافات** — مع بلوك الترقية (P0-4).
3. **بياناتك** — 3 حقول.
4. زر واحد.

### 🟠 P1-4 — الإضافات مش مفلترة بالشخصية

**الملاحظة:** كل الإضافات التلاتة بتتعرض لكل الشخصيات.

**الدليل من الكود:**
```tsx
{ADDONS.map((item) => { ... })}
```


### 🟠 P1-7 — مفيش تحقّق فعلي من المدخلات

**الملاحظة:** الحقول التلاتة معتمدة على `required` بس.

**الدليل من الكود:**
```tsx
<Input id="customer-phone" name="phone" placeholder="01xxxxxxxxx" required dir="ltr" inputMode="tel" ... />
```
`inputMode="tel"` صح ✅، لكن مفيش `pattern` ولا تحقّق لحظي ولا رسالة خطأ عربية.

**الأثر البيعي:** رقم موبايل غلط = ليد ميت. وإنت بتستخدم نفس الرقم للواتساب (الليبل بيقول «واتساب»)، فأي خطأ رقم واحد بيقطع قناة المتابعة كلها. والرسائل الافتراضية للمتصفح بتطلع بالإنجليزي وبشكل مش متسق مع الصفحة.

**الإصلاح:**
1. `pattern="01[0125][0-9]{8}"` + `maxLength={11}` للموبايل المصري، مع رسالة: «الرقم لازم يبدأ بـ010 أو 011 أو 012 أو 015 ويكون 11 رقم».
2. تحقّق لحظي عند `onBlur` — علامة ✓ خضراء لما يبقى صح. التأكيد الإيجابي بيقلل القلق أكتر من رسالة الخطأ بكتير.
3. نظّف المدخل تلقائيًا: شيل المسافات والشرطات وحوّل الأرقام العربية للاتينية قبل الإرسال.
4. الـplaceholder بيقول «مثال: مكتب النيل للمحاسبة والمراجعة` لكل الشخصيات، والليبل هو اللي بيتغيّر:
   ```tsx
   {persona === "firm" ? "اسم المكتب / المسؤول" : "اسم الشركة أو النشاط التجاري"}
   ```
   خلّي الـplaceholder يتغيّر مع الليبل. شركة بتشوف مثال لمكتب محاسبة = إشارة تانية إن الصفحة مش بتاعتها.

## 3. الأنيميشن — إيه اللي يستاهل حركة على صفحة دفع

القاعدة على الشيك أوت مختلفة عن صفحة الهبوط: **الحركة هنا وظيفتها تأكيد، مش جذب.** أي أنيميشن ديكوري على صفحة دفع بيقرأ كبطء أو كعدم جدية.

| العنصر | الحركة | المدة | السبب |
|---|---|---|---|
| الإجمالي عند التغيير | `count-up` + وميض خلفية خفيف | 250ms | يربط الفعل بالنتيجة — أهم حركة في الصفحة |
| بلوك الترقية (P0-4) | ظهور متتابع: 250 → 600 → `=` → 850 → البونصين | 70ms بين كل سطر | الحركة بترسم الحجة البيعية خطوة بخطوة |
| كارت الإضافة عند الاختيار | `scale(1.015)` + انتقال الحدود | 150ms | تأكيد لمسي فوري |
| stepper الكمية | الرقم يعمل slide لأعلى/أسفل حسب الاتجاه | 120ms | يمنع الإحساس إن الضغطة ماحصلتش |
| شريط التقدّم | `transition-[width]` | 300ms | إحساس التقدّم |
| زر الإرسال عند التحميل | spinner + النص يتغيّر | — | موجود ✅ |
| كارت الملخص | **بدون** حركة دخول | — | معلومة مرجعية، لازم تكون ثابتة ومتاحة |

**إلزامي:** ضيف
```css
@media (prefers-reduced-motion: reduce) { /* عطّل كل الترانزيشنات */ }
```
ده مش موجود في `index.css` خالص (متسجّل في تقرير LP-A)، وعلى صفحة دفع بقى مسألة إتاحة مش تحسين.

| `og:*` | صورة نسبية مكسورة موروثة | ملهاش لزوم مع noindex | 🟡 P2 |
| `maximum-scale=1` | موروث من `index.html` | شيله — بيمنع التكبير على صفحة فيها أرقام صغيرة | 🟠 P1 |
